# 验证集 ROUGE：SFT(step_000336) vs GRPO(v48)

**一句话结论**：在同一份 1340 条验证集、同一套官方 ROUGE 口径下，GRPO 后的
模型**稳定但小幅**优于 SFT —— 综合分 +0.0059（char）/ +0.0070（jieba），两套
分词口径的成对 bootstrap 区间都不含 0。但增益并不普遍：**中位差为 0**（一半以上
样本几乎没动），净增益的约 2/3 来自 20 条样本，同时有 192 条掉分超过 0.05。

---

## 一、先对齐口径（这是"数字能不能比"的前提）

ROUGE 实现和评测路径都在 `src/sfzy/eval/rouge.py`，三条规则决定了数字长什么样：

1. **逐样本算分，再对样本取宏平均**（`score_corpus`）。把所有人的预测拼起来算
   一次是另一种口径，数值不同 —— 本项目一律用宏平均。
2. **只在双方共有的 id 上比**。哪个模型少跑了几条，差值里不该混进"谁多做了
   几条"。本次两边都覆盖了全部 1340 条，所以这条没造成差异，但流程上仍然按它走。
3. **综合分 = 0.2·ROUGE-1-F + 0.4·ROUGE-2-F + 0.4·ROUGE-L-F**
   （`OFFICIAL_WEIGHTS`）。不是三项简单平均：ROUGE-2 与 ROUGE-L 各占 0.4，
   所以**短语搭配和词序的权重是单个字覆盖的两倍**。

分词口径有两套，两套都算了，因为项目里两条路默认值不同：

| 口径 | 谁在用 | 特点 |
|---|---|---|
| `char` | `scripts/evaluate.py` 默认、对外报分 | 按字符切、丢弃空白 |
| `jieba` | `RewardSpec.rouge_mode` 默认（训练奖励与 `eval/*` 监控） | 按词切 |

两套的**绝对分不可混用**（jieba 的 R2 明显低于 char），结论方向则应该一致；
如果不一致，说明结论对分词敏感，不能当结论。

## 二、评的是什么数据

| 文件 | 条数 | 说明 |
|---|---|---|
| `data/triples/sft_val_shard0of2.jsonl` + `shard1of2.jsonl` | 670 + 670 | SFT(step_000336) 的输出，两个分片按 id 合并（分片间 0 重叠） |
| `data/triples/grpo_val_v48.jsonl` | 1340 | GRPO(v48) 的输出 |
| `data/splits/val.jsonl` | 1340 | 参考摘要（键 `id`/`summary`） |

核对结果：两份输出的 `reference` 字段与 `data/splits/val.jsonl` 的 `summary`
**逐条相同（0 条不一致）**，id 覆盖完整、无重复。所以这是一次干净的同一数据集对比。

## 三、结果

### char 口径（对外报分用这个）

| 模型 | ROUGE-1-F | ROUGE-2-F | ROUGE-L-F | 综合分 | 输出均长 |
|---|---|---|---|---|---|
| SFT `step_000336` | 0.7111 | 0.5815 | 0.6237 | **0.6243** | 302.5 字 |
| GRPO `v48` | 0.7161 | 0.5876 | 0.6298 | **0.6302** | 303.6 字 |
| 差值 | +0.0050 | +0.0060 | +0.0061 | **+0.0059** | +1.1 字 |

### jieba 口径（训练奖励/监控口径）

| 模型 | ROUGE-1-F | ROUGE-2-F | ROUGE-L-F | 综合分 |
|---|---|---|---|---|
| SFT `step_000336` | 0.6660 | 0.4883 | 0.5920 | **0.5653** |
| GRPO `v48` | 0.6726 | 0.4953 | 0.5991 | **0.5723** |
| 差值 | +0.0066 | +0.0070 | +0.0071 | **+0.0070** |

三项指标同向、两个口径同向 —— 没有出现"某一项涨、综合分靠权重撑起来"的情况。
相对提升约 +0.9%（char）/ +1.2%（jieba）。

## 四、这个差值稳不稳？拆开看

成对比较（同一条样本一起重采样，10000 次 bootstrap，seed=42）：

| 口径 | 综合分差 | 成对 95% 区间 | 赢 / 平 / 输 | 符号检验 p |
|---|---|---|---|---|
| char | +0.0059 | [+0.0017, +0.0101] | 664 / 124 / 552 | ≈1.4e-3 |
| jieba | +0.0070 | [+0.0025, +0.0115] | 660 / 129 / 551 | ≈1.9e-3 |

区间不含 0、胜负比接近 6:5，方向是可信的。但下面三条说明**这不是"整体变好"**：

1. **中位差 = 0.0000**：一半以上样本的分数动得极小。差值分布（char）：
   p10 −0.074 / p25 −0.020 / p50 0.000 / p75 +0.032 / p90 +0.094。
   赢的 664 条平均 +0.0555，输的 552 条平均 −0.0525 —— 是**有涨有跌的重排**，
   不是水位整体抬升。**掉分超过 0.05 的有 192 条**（jieba 204 条）。
2. **净增益高度集中**：增益最大的 20 条贡献 +5.47，占全部净增益 +7.88 的 **69%**。
   去掉这 20 条，均值只剩 **+0.0018**（jieba +0.0027）—— 仍是正的，但已接近噪声量级。
3. **121 条输出与 SFT 逐字相同**（差值恰为 0，符合预期）。在输出确实变了的
   1219 条上，Δ 综合分 +0.0065，赢 664 / 输 552。

### 增益出现在哪类样本上

按参考摘要长度把 1340 条四等分（char 口径、输出与参考均按字数）：

| 参考长度分层 | 平均参考长度 | Δ综合分 | 赢的条数 |
|---|---|---|---|
| 短 1/4 | 226 字 | +0.0003 | 158 / 335 |
| 中 2/4 | 282 字 | −0.0038 | 142 / 335 |
| 中 3/4 | 298 字 | +0.0122 | 179 / 335 |
| 长 1/4 | 317 字 | +0.0148 | 185 / 335 |

**收益几乎全部来自较长的样本，短样本基本没动（甚至略降）**。这和"GRPO 让要素
覆盖更完整"的预期方向一致（长文要素更多，漏要素的代价更大），但这里只是相关性，
要下这个结论得看要素覆盖率与事实一致性的分项指标（见 `docs/grpo_monitoring.md`
的 `eval/coverage_mean`、`eval/fact_mean`）。

**长度不是解释**：输出均长只从 302.5 涨到 303.6 字，同一条样本的长度比均值
1.0208 —— 不是靠多写字换来的分。疑似被 `max_new_tokens` 截断的输出（结尾无句末
标点）SFT 15 条、GRPO 11 条，量级不足以影响结论。

## 五、结论

1. **GRPO 这一步是正收益**，幅度约 +0.6~0.7 个点（相对 +1%），在两个分词口径下
   都成立、成对检验都显著。可以按"GRPO 比 SFT 好一点"记录。
2. **但不要把 +0.006 读成"全面提升"**：中位差为 0、192 条掉幅超 0.05、净增益的
   近 2/3 由 20 条样本贡献。继续调优时，值得抽看这 20 条赢在哪、那 192 条输在
   哪里 —— 这比再刷一个总数更有信息量。
3. **方向性发现**：收益集中在长文书，短样本无收益。如果后续要提高短样本，
   得往别的方向调（短样本的瓶颈大概率不是要素覆盖）。
4. **ROUGE 只能证明"表层更像参考"**，它对数字抄错、结论反转、幻觉都不敏感
   （项目自己的压力测试见 `docs/semantic_metrics.md` 与 `tools/bench_metrics.py`）。
   要说明"GRPO 让摘要更准"，需要同一份数据上再跑一遍 judge 类指标。

### 局限（读数字时要带着）

* 每个样本只有**一次生成**（`--num 1` 贪心），没有同 prompt 的多次采样，因此
  无法把"生成随机性"这个方差来源也估进去 —— 上面所有区间都只是**样本维度**的。
  前提是两份输出用了同一套解码参数（SFT 那份是脚本默认的贪心；GRPO 那份的生成
  参数建议确认一次）。
* 单次对比、单份数据集（val 固定 1340 条），不构成"GRPO 一定更好"的普适结论。
* 差值对 20 条样本敏感，说明它**不够稳健到可以做小改动之间的排序依据**。

## 六、怎么复现

```bash
# 一份命令出全部表格（含成对 bootstrap、分布、逐样本分数）
python tools/compare_val_rouge.py \
    --pred sft='data/triples/sft_val_shard*of2.jsonl' \
           grpo_v48=data/triples/grpo_val_v48.jsonl \
    --ref data/splits/val.jsonl \
    --json outputs/val_rouge_sft_vs_grpo_v48.json
```

`tools/compare_val_rouge.py` 的默认分词是 `char,jieba`（两套都算），第一份
`--pred` 作为基线。逐样本分数落在 `outputs/val_rouge_sft_vs_grpo_v48.json`
（`modes.<mode>.per_sample`），本文第四节的分布与分层都是从这个文件算出来的。
工具内部会用 `score_corpus` 再算一遍对账（宏平均口径不一致会直接 assert 失败），
避免"手算宏平均"和项目评测路径悄悄分叉。

按 id 看某一条的具体涨跌：

```bash
python - <<'PY'
import json
d = json.load(open("outputs/val_rouge_sft_vs_grpo_v48.json"))
ps = d["modes"]["char"]["per_sample"]
diff = {i: ps["grpo_v48"][i]["overall"] - ps["sft"][i]["overall"] for i in d["ids"]}
top = sorted(diff.items(), key=lambda kv: -kv[1])[:10]     # 赢最多 / 输最多的各 10 条
print("赢:", top)
print("输:", sorted(diff.items(), key=lambda kv: kv[1])[:10])
PY
```
